## 결정

### 1. 특화 분야

**"하지 않아도 될 일을 하지 않는 미니 React — 그리고 그것이 맞다는 증명"**

- 성능(perf): 대량 목록에서 DOM 변경·패치·diff 작업을 줄이고 숫자로 보여 준다.
- 정확성(dx): 브라우저 파서를 정답지로 쓰는 차등 fuzz로 "줄였어도 결과가 같다"를 증명한다.
- 학습(기존 강점): 데모가 이 숫자를 보여 주고, 같은 문제에 React·Vue가 고른 답과 비교한다.

세 제안서 모두 A안(lead)에 동의했고, perf는 범위를 "DOM에 영향 없는 패치·diff 비용"까지, dx는 "정확성 증명"까지 넓혔다. 둘 다 채택한다.

### 3. 성능 예산

**강한 예산 (CI, `tests/bench/budget.test.js`, 넘으면 병합하지 않음).** 시나리오별 상한, 결정적 지표 넷:

1. 패치 수
2. MutationObserver 기록 수
3. 기록 안의 addedNodes + removedNodes 합 (실제로 붙이고 뗀 노드 수)
4. 새로 만든 DOM 노드 수

②만 걸면 fragment·replaceChildren이 지표를 1로 만들어 "줄었다"를 과장할 수 있으므로 ③④를 함께 적는다(dx 수정안).
"패치 수 = 기록 수" 같은 등식은 쓰지 않는다(MOVE는 기록 2, 프로퍼티 PROPS는 기록 0).
상한은 `feat/perf-bench`에서 현재 기준선 값으로 시작하고, 각 최적화 브랜치가 자기 개선분만큼 상한을 낮춘다(낮춘 값이 다음 기준).

**약한 예산 (기록만).** diff ms·patch ms 중앙값(1k 11회, jsdom). 직전 기준보다 20% 넘게 느려지면 PR 본문 "남은 경고"에 적고 이유를 설명한다. 시간은 환경 잡음(±30%)이 커서 CI 실패 조건으로 쓰지 않는다. 브라우저 수치는 P2-a 페이지에서 브라우저·버전·기기와 함께.

**정확성 예산 (CI).** 기존 테스트 전부 + 차등 fuzz 불일치 0. 차등 fuzz가 CI에 더하는 시간 ≤ 3초.

### 4. 측정 방법

| 지표 | 도구 | 비고 |
|---|---|---|
| 패치 수·종류 | `render()` 반환값 | 결정적 |
| 기록 수, added+removed 합 | MutationObserver `takeRecords()` | 결정적 |
| 새 DOM 노드 수 | 하네스에서 `document.createElement*`·`createTextNode` 호출 계측 | 결정적 |
| diff/patch ms | `performance.now()`, 11회 중앙값, **실행마다 새 jsdom 창** | jsdom, 참고용. 10k는 메모리 때문에 1회 |
| 프로파일 | `node --cpu-prof` 스크립트 | 최적화 근거로만 |
| 정확성 | 차등 fuzz (오라클 = `innerHTML` 파싱 결과 + 폼 프로퍼티) | 시드 고정 |

시나리오: 생성(이전 없음/빈 tbody), 전체 교체, 10행마다 갱신, 한 행 선택, swap, 맨 뒤→맨 앞, 뒤집기, 한 행 삭제, 1k 뒤 1k 추가, 같은 데이터 다시 렌더, 전체 지우기, **attach로 읽은 실제 DOM(들여쓰기 공백 포함)에서 시작하는 변형**. 핸들러는 실제 앱처럼 렌더마다 새 함수.

## 버린 안과 이유

| 안 | 이유 |
|---|---|
| 기록 수(②)만으로 성능 예산 | 묶기 최적화가 지표를 속일 수 있음 (dx 수정안, ③④ 추가로 대체) |
| "패치 수 = DOM 변경 기록 수" 불변식 | MOVE(기록 2)·프로퍼티 PROPS(기록 0) 때문에 등식이 성립하지 않음 |
| 연속 CREATE 묶기의 이득을 jsdom 시간으로 주장 | 실행마다 새 창으로 재측정하니 하나씩 105ms ≈ 한 번에 106ms. 한 문서를 계속 쓴 첫 측정(466ms)은 남은 노드 때문에 부풀었음 (perf 정정) |
| 시간을 CI 실패 조건으로 | jsdom 시간이 실행마다 ±30% 흔들림 (perf 측정) |
| B3를 attach 트리에서도 텍스트 병합으로 해결 | vnode 1개가 DOM 노드 2개를 대표하게 되어 다음 TEXT 패치가 "abb"처럼 틀림 (lead 지적, dx 설계 변경) |
| 이벤트 위임을 P1로 | 버블링 안 하는 이벤트·전파 순서 위험이 크고, 핸들러 교체 비용은 P1-b로 사라짐. 측정 후 이득 10% 미만이면 하지 않음 |
| memo를 P1로 | API 추가·캐시 무효화 위험. 핸들러 props 때문에 실제 앱에서 효과가 불확실 → P1 뒤 측정 조건부 |
| devtools 패널·패치 재생(dx P3)을 지금 | 종합 페이지와 겹침. P1·P2 뒤로 |
| 학습 도구(B안)를 간판 특화로 | 이미 강점이지만 수치로 차별화하기 어려움. A안의 결과를 보여 주는 화면으로 둠 |

## 결과

- 좋은 점: 차별점이 "숫자 + 증명"으로 한 문장이 된다. 강한 예산이 결정적이라 CI에서 회귀를 막는다.
- 비용: patch.js·diff.js에 빠른 경로가 늘어 코드가 길어진다 → 빠른 경로마다 "왜·언제" 주석과 테스트 이름, 설명 못 하는 최적화는 받지 않는다.
- 남는 한계: jsdom 시간은 브라우저와 다르다(브라우저 페이지로 보완). B4(사용자 직접 조작)는 비제어 컴포넌트와 같은 설계 한계로 남기고 drift 감지로 보여 준다.
