# LIS 기반 keyed 재조정의 성능 특성과 적용 조건

- 측정일: 2026-11-09 · 커밋: `5c6fe15` (`feat/lis-experiment`)
- 원자료: [`lis-data/2026-11-09.csv`](lis-data/2026-11-09.csv) (전체 JSON은 실험 페이지의 "결과 JSON 내보내기")
- 실험 페이지: `npm run serve` → `/demo/bench/lis.html` · 하네스: `scripts/bench/lis-harness.js`

## 요약

이 환경(Chrome 152, Windows, 1,000행 기준)에서 관찰한 것:

1. **LIS는 diff 비용을 조금 늘리고 commit 비용을 크게 줄였다.** 같은 갱신에서 A(LIS)의 T_Diff 중앙값은 B(단방향 스캔)보다 2~6% 높았다(IQR은 겹친다). 대신 일부만 옮기는 갱신에서 옮긴 기존 노드 수가 크게 줄어 T_Commit이 줄었다. 예: 1% 이동 0.645 → 0.015ms, swap 0.72 → 0.01ms.
2. **이득은 "일부만 옮길 때"에 몰려 있다.** 이동 비율 k가 1~10%일 때 A의 T_JS는 B의 약 0.6배였다. 이 비율은 k=25% 0.70, 50% 0.79, 100% 0.99로 1에 가까워졌다. 거의 다 섞이면 LIS 밖 노드가 대부분이라 옮길 노드 수가 비슷해지고(944 vs 990), 남는 것은 diff 쪽 추가 비용이다.
3. **LIS가 불리하거나 이득이 없는 조건도 있었다.**
   - 전체 셔플: N=5000, k=100%에서 A의 T_JS 중앙값이 B보다 높았다(10.97 vs 10.58ms, IQR 겹침).
   - 뒤집기·한 덩어리 이동(blockShift): 두 방식이 옮기는 노드 수가 같아 이득이 0이다.
   - 항목 내부가 큰 경우(항목당 요소 10·50개): 하위 트리 비교가 diff의 대부분이라 이동 판단의 차이가 묻힌다.
4. **React 18.3.1이 실제로 옮긴 노드 수는 모든 조건에서 B와 같았다.** B가 React의 이동 규칙을 재현한다는 근거다. React와의 시간 비교는 참고용이다. 작은 N과 덩어리 이동에서는 React가 빨랐고, N=5000 셔플에서는 느렸다. 원인은 이 실험으로 가를 수 없다.
5. **시간 측정의 흔들림이 컸다.** IQR/중앙값이 모든 조건에서 5%(파일럿 운영 기준)를 넘었다(10~87%). 그래서 63회까지 늘렸다. 따라서 10% 안팎의 시간 차이는 결론으로 쓰지 않는다. 옮긴 노드 수 같은 결정적 지표가 이 보고서의 1차 근거다.

## 1. 질문과 비교 대상

질문: key 목록을 재정렬할 때 "그대로 둘 노드"를 LIS(최장 증가 부분 수열)로 고르는 방식은 언제 유리하고 언제 불리한가.

| | 내용 |
|---|---|
| **A** | mini-react + LIS (`diff(old, new, { reconcileMode: 'lis' })`, 기본값) |
| **B** | mini-react + 단방향 스캔 (`reconcileMode: 'lastPlacedIndex'`). React의 접근을 참고한 자체 구현: `lastPlacedIndex = 0`, 새 순서대로 이전 위치가 `lastPlacedIndex`보다 작으면 MOVE, 아니면 `lastPlacedIndex`를 그 위치로 |
| **C** | React 18.3.1 + ReactDOM 프로덕션 빌드, `flushSync`로 동기 커밋. **참고용 기준선**이다. 구현 전체가 다르므로 A·C 차이의 원인을 이동 판단 하나로 돌리지 않는다 |

A와 B의 차이는 이동 판단 함수 하나뿐이다(`src/diff/diff.js` `placeMiddle`의 `stays` 계산). 두 모드는 다음을 같이 쓴다: 앞뒤 공통 구간 건너뛰기, key 맵, 앵커(before) 결정, patch, 핸들러 상자, Fragment 일괄 삽입. 판단은 diff 안에서만 하고 patch는 받은 목록을 실행만 한다. `stats` 옵션으로 실행마다 경로를 기록했다. 아래의 모든 재정렬 조건은 "앞뒤 건너뛰기 뒤 가운데 구간을 key로 짝짓고 이동 판단을 1회 실행"한 경로였다(keyedMatch 1, placementRuns 1).

**사실과 가설의 구분**
- 사실: React는 자식 배열 재조정에서 `lastPlacedIndex` 방식을 쓰고(ReactChildFiber `placeChild`), Vue 3는 LIS를 쓴다(`patchKeyedChildren`의 `getSequence`).
- 가설(검증하지 않음): React가 LIS를 쓰지 않는 이유는 실제 앱의 목록 갱신이 대부분 추가·삭제·한 곳 이동이라 LIS의 추가 비용과 복잡도에 비해 이득이 작다고 봤기 때문일 수 있다. Fiber의 한 방향 순회 구조와 맞추기 위해서일 수도 있다.

## 2. 방법

**작업** (`scripts/bench/keyed-workloads.js`)
- 목록: `<ul>` 아래 key 있는 항목 N개.
- 기준점: N=1000, 무작위 셔플(Random Shuffle), 항목 복잡도 Level 1(`<li>텍스트</li>`), 재정렬만.
- 축은 한 번에 하나씩 바꿨다.
  - 크기 N ∈ {10, 50, 100, 500, 1000, 5000}
  - 이동 비율 k ∈ {1, 5, 10, 25, 50, 100}%: 노드 k%를 골라 빼고 무작위 자리에 다시 넣는다.
  - 패턴: Swap(1번과 N−2번 자리), Block Shift(10% 덩어리를 다른 자리로), Full Reversal, Random Shuffle
  - 복잡도: 깊이 3 고정 `<li><div><span>…</span></div></li>`, 항목당 요소 {3, 10, 50}개. 내부 텍스트·속성은 갱신 전후 같다.
  - 보조: 마지막 항목 텍스트 변경, 1개 추가, 1개 삭제.
- x축 P_nonLIS = (N − |LIS|) / N × 100은 사후에 계산했다. 여기서 N은 생존 노드 수, LIS는 "이전 위치를 새 순서로 늘어놓은 수열"의 LIS다.
- 조건마다 시드와 LIS 길이, 실제로 옮긴 수를 원자료에 남겼다.
- 변곡점이 보인 구간(이동 비율 50→100%)만 2변수 실험(N ∈ {100, 1000, 5000} × k ∈ {25, 50, 75, 100}%)을 더 했다.

**시간**
- T_Diff = `diff` 호출~반환.
- T_Commit = `patch` 호출~반환(DOM 조작 + 핸들러 표 교체).
- T_JS = 둘의 합. C는 둘이 나뉘지 않으므로 `flushSync(() => root.render(next))` 전체를 T_JS로 쟀다.
- 컨테이너 준비, 처음 그리기, 다음 가상 트리(React 요소) 만들기는 타이머 밖이다.
- 웜업 5회 + 21회. IQR/중앙값이 5%를 넘으면 21회씩 최대 63회까지 늘렸다(파일럿 운영 기준).
- 반복마다 A·B(·C) 순서를 교대했다.
- N<100은 컨테이너 100개를 미리 그려 두고, 한 타이머 구간에서 100번 갱신한 시간을 100으로 나눴다.
- N=100·500은 배치와 단일 두 방식을 모두 쟀다.
- `performance.now()`의 최소 간격(0.005ms)과 호출 비용(262ns)은 기록만 했다. 빈 루프 시간은 빼지 않았다.
- 실험 페이지는 교차 출처 격리(COOP/COEP)로 열었다. 격리하지 않으면 해상도가 0.1ms라 1ms 안팎의 값을 가를 수 없다.
- 강제 layout(`offsetHeight`) 시간은 이번 실행에서 재지 않았다.

**DOM 지표** (`scripts/bench/dom-counter.js`)
- 시간 측정과 따로, 계수기를 붙인 실행을 조건마다 1회 했다.
- 계측 API: `insertBefore`·`appendChild`·`removeChild`·`remove()`·`replaceWith()`·`textContent=''`(지워진 자식 수로 셈).
- 1차 지표는 movedExistingNodes(측정 창 시작 때 있던 노드를 다른 자리로 넣은 수)다. 같은 자리 재삽입은 이동으로 세지 않는다. Fragment를 거친 기존 노드는 출처 추적(WeakSet)으로 이동으로 센다.
- DOM에 key 속성은 쓰지 않았다. 노드 정체성은 갱신 전후 가상 트리의 key → 실제 노드 맵으로 비교했다.

**환경**
- Chrome 152.0.7977.167 (Claude 데스크톱 앱 내장 브라우저, 창이 보이는 상태)
- Windows, 논리 코어 12, 메모리 16GB, 전원 연결
- React·ReactDOM 18.3.1 프로덕션 UMD (devDependency 버전 고정, 로컬 서빙)

## 3. 성능 측정 전 검사

**정확성** (`node scripts/fuzz-keyed.js`, CI는 `tests/diff/keyed-modes.test.js`·`tests/diff/reconcile-mode.test.js`)
- 두 모드 각각과 모드 사이에서 네 가지를 확인했다.
  - 최종 DOM(구조·태그·속성·텍스트·순서)이 처음부터 그린 것과 같다.
  - key 순서가 목표와 같다.
  - 생존 key의 노드가 같다(===).
  - 새 key가 이전 노드를 다시 쓰지 않는다.
- keyed 집중 fuzz 1,000쌍과 일반 트리 fuzz 1,000쌍을 따로 돌렸다.
  - keyed 쪽은 N=0~39, 삽입·삭제·이동·텍스트 변경 혼합, 복잡도 1·3·10이다.
  - 앞뒤 건너뛰기만 탄 목록과 key 매칭까지 간 목록이 모두 나왔다.
- 결과: 이 생성기로는 왜곡을 탐지하지 못했다.
- 경계 사례(N=0·1·2 등)는 별도 테스트로 확인했다. 중복 key는 생성기에서 막았다. 지금 동작(경고 후 목록 전체를 위치로 비교)은 별도 테스트로 기록했다.
- 패치 수·이동 수가 모드끼리 같은지는 기준으로 삼지 않았다. 그것이 종속변수다.

**계수기 검증** (`tests/bench/dom-counter.test.js`)
- 일곱 가지 경우를 단위 테스트했다: 신규 삽입, 기존 이동, 삭제, fragment로 기존 이동, fragment로 신규 삽입, 위치 변화 없는 삽입, 컨테이너 밖 변경.
- `fn`이 던져도 원래 메서드가 복원되는지도 확인했다.
- 엔진에 붙여 10개 swap을 셌다: A 2, B 7.

## 4. 결과

표의 시간은 ms 중앙값이다. 괄호는 T_JS의 [Q1–Q3]이다. "이동"은 옮긴 기존 노드 수(A / B / C)다.

### 4.1 기준점: N=1000, 무작위 셔플

| | T_Diff | T_Commit | T_JS | 이동 |
|---|---:|---:|---:|---:|
| A (LIS) | 0.890 | 0.735 | 1.635 [1.580–1.753] | 944 |
| B (단방향) | 0.865 | 0.785 | 1.645 [1.578–1.775] | 990 |
| C (React) | – | – | 0.890 [0.840–0.965] | 990 |

LIS는 46개를 덜 옮겼다(−4.6%). 그 대가로 T_Diff 중앙값이 0.025ms 높았다. T_JS는 사실상 같다.

### 4.2 이동 비율 k (N=1000) — LIS의 이득이 가장 크게 갈리는 축

| k | P_nonLIS | A T_Diff | B T_Diff | A T_Commit | B T_Commit | A T_JS | B T_JS | A/B | 이동 A / B |
|---:|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| 1% | 1.0 | 0.850 | 0.820 | 0.015 | 0.645 | 0.865 | 1.470 | 0.59 | 10 / 869 |
| 5% | 5.0 | 0.920 | 0.880 | 0.055 | 0.770 | 0.970 | 1.640 | 0.59 | 50 / 985 |
| 10% | 10.0 | 0.920 | 0.900 | 0.100 | 0.790 | 1.025 | 1.695 | 0.60 | 100 / 980 |
| 25% | 25.0 | 1.050 | 0.990 | 0.270 | 0.905 | 1.325 | 1.895 | 0.70 | 250 / 989 |
| 50% | 49.9 | 0.910 | 0.870 | 0.450 | 0.815 | 1.355 | 1.710 | 0.79 | 499 / 993 |
| 100% | 94.2 | 0.915 | 0.895 | 0.755 | 0.790 | 1.670 | 1.690 | 0.99 | 942 / 996 |

- A의 이동 수는 P_nonLIS × N과 같다(이론 최소). B는 k=1%에서도 869개를 옮겼다.
  - 무작위 자리로 옮긴 노드 하나가 앞쪽으로 가면, 단방향 스캔은 그 뒤에 남은 노드들을 "앞에 있던 것"으로 보고 옮긴다.
- T_Commit은 옮긴 노드 수에 거의 비례했다. B 기준 노드당 약 0.75µs다.
- T_Diff의 A−B 차이(중앙값 +0.02~0.06ms)는 k와 뚜렷한 관계가 없었다.

### 4.3 2변수: N × k (A T_JS / B T_JS)

| N \ k | 25% | 50% | 75% | 100% |
|---:|---:|---:|---:|---:|
| 100 | 0.75 | 0.80 | 0.92 | 0.97 |
| 1000 | 0.71 | 0.74 | 0.91 | 0.93 |
| 5000 | 0.67 | 0.80 | 0.90 | **1.04** |

- 크기와 관계없이 k가 커질수록 1에 가까워졌다.
- N=5000, k=100%에서는 A가 중앙값 기준으로 느렸다: 10.97 [10.21–12.49] vs 10.58 [10.07–11.68]ms. IQR이 겹쳐 차이를 단정할 수는 없다. 다만 "옮길 노드를 거의 줄이지 못할 때(4867 vs 4992) LIS의 diff 비용(5.41 vs 5.21ms)이 남는다"는 방향과는 맞는다.

### 4.4 패턴 (N=1000)

| 패턴 | P_nonLIS | A T_JS | B T_JS | C T_JS | 이동 A / B / C |
|---|---:|---:|---:|---:|---:|
| Swap | 0.2 | **0.885** | 1.560 | 1.850 | 2 / 997 / 997 |
| Block Shift (10%) | 10.0 | 0.705 | 0.695 | **0.280** | 100 / 100 / 100 |
| Full Reversal | 99.9 | 1.640 | 1.610 | 1.830 | 999 / 999 / 999 |
| Random Shuffle | 94.3 | 1.625 | 1.615 | **1.030** | 943 / 995 / 995 |

- **Swap**은 LIS가 가장 유리한 경우다. 단방향 스캔은 뒤쪽 노드를 앞으로 보낸 순간 그 사이 노드를 모두 옮긴다(997개).
- **Block Shift**(이번 시드는 덩어리가 뒤로 감)와 **Full Reversal**은 두 방식이 옮기는 수가 같다. LIS의 이득은 0이고, 시간도 같았다.
  - 덩어리를 앞으로 보내는 경우에는 B의 이동 수가 늘어난다(2변수 실험 범위 밖, 한계 참고).

### 4.5 크기 N (무작위 셔플)

| N | P_nonLIS | A T_JS | B T_JS | C T_JS | 이동 A / B / C | 방식 |
|---:|---:|---:|---:|---:|---:|---|
| 10 | 60.0 | 0.0164 | 0.0172 | 0.0106 | 6 / 7 / 7 | 배치 |
| 50 | 78.0 | 0.0767 | 0.0810 | 0.0352 | 39 / 44 / 44 | 배치 |
| 100 | 85.0 | 0.160 | 0.160 | 0.075 | 85 / 95 / 95 | 단일 |
| 500 | 92.0 | 0.880 | 0.885 | 0.590 | 460 / 494 / 494 | 단일 |
| 1000 | 94.4 | 1.635 | 1.645 | 0.890 | 944 / 990 / 990 | 단일 |
| 5000 | 97.4 | 10.440 | 10.480 | 16.830 | 4870 / 4991 / 4991 | 단일 |

- 무작위 셔플에서는 N이 커질수록 P_nonLIS가 100%에 가까워진다. 그래서 A와 B의 차이는 모든 N에서 측정 흔들림 안이었다.
- 배치와 단일 측정의 일치:
  - N=100: A T_JS 0.160(단일) vs 0.172(배치), 7% 차이.
  - N=500: 0.880 vs 0.996, 13% 차이.
  - 배치가 일관되게 조금 높았다(캐시·GC 영향으로 추정, 검증 안 함).

### 4.6 항목 복잡도 (N=1000, 무작위 셔플)

| 요소/항목 | A T_Diff | A T_Commit | A T_JS | B T_JS | 이동 A / B |
|---:|---:|---:|---:|---:|---:|
| 1 | 0.890 | 0.735 | 1.635 | 1.645 | 944 / 990 |
| 3 | 1.895 | 1.155 | 3.055 | 3.095 | 938 / 989 |
| 10 | 7.430 | 2.420 | 9.855 | 10.455 | 942 / 993 |
| 50 | 50.695 | 7.070 | 57.820 | 59.880 | 944 / 996 |

- 항목이 커지면 T_Diff가 급격히 늘었다(1 → 50요소에서 57배). 짝지은 항목마다 하위 트리를 비교하기 때문이다.
- 옮기는 노드 수는 그대로라 이동 판단의 차이는 전체의 몇 %에 묻혔다.
- T_Commit도 커졌다(0.735 → 7.07ms). 옮기는 노드 수는 같으므로, 무거운 하위 트리를 옮기는 비용이 큰 것으로 보인다(가설).

### 4.7 보조 조건 (N=1000)

| 갱신 | A T_JS | B T_JS | 경로(A) | 이동 |
|---|---:|---:|---|---:|
| 마지막 항목 텍스트 변경 | 0.670 | 0.705 | 모든 목록이 앞뒤 건너뛰기만 | 0 |
| 1개 추가 | 0.610 | 0.590 | key 매칭 1회, 이동 판단 1회 | 0 (CREATE 1) |
| 1개 삭제 | 0.710 | 0.710 | key 매칭 1회, 이동 판단 생략 | 0 (REMOVE 1) |

순서가 바뀌지 않는 흔한 갱신에서는 두 방식이 같은 경로를 탔다. 이동 판단 비용이 없거나 무시할 만했다.

### 4.8 React 기준선 (참고)

- **이동 수:** 측정한 모든 조건(크기 6개, 패턴 4개)에서 React 18.3.1의 movedExistingNodes가 B와 정확히 같았다.
- **시간:**
  - React가 더 빨랐던 조건: N ≤ 1000 셔플(약 0.55~0.65배), Block Shift(0.280 vs 0.705ms).
  - React가 더 느렸던 조건: N=5000 셔플(16.83 vs 10.44ms), Swap(1.85 vs 0.885ms), Reversal(1.83 vs 1.64ms).
- 이 차이에는 가상 노드 구조, 훅·Fiber 처리, 이벤트 시스템 등 이동 판단 밖의 요인이 모두 섞여 있다. 그래서 인과를 주장하지 않는다.
- Swap에서 React가 느린 것은 B와 같은 수(997개)를 옮기기 때문으로 보인다(이동 수는 사실, 시간 연결은 가설).

## 5. 해석

- **언제 LIS를 쓰나:** 목록의 일부만 순서가 바뀌는 갱신(드래그로 한 항목 옮기기, 두 항목 교환, 일부 재정렬)에서 LIS는 commit 비용을 크게 줄였다. 이때 diff 쪽 추가 비용은 측정 흔들림 수준이었다.
- **언제 이득이 없나:**
  - 목록 대부분이 섞이는 갱신(전체 셔플, 무작위 정렬 변경)
  - 단방향 스캔도 최소로 옮기는 패턴(뒤집기, 뒤쪽으로 덩어리 이동)
  - 순서가 바뀌지 않는 갱신(추가·삭제·텍스트 변경)
  
  이런 갱신에서는 이득이 없거나, 아주 큰 목록에서 diff 쪽 비용만 남을 수 있다.
- **비율로 말하면:** 이 환경에서 T_JS 이득은 P_nonLIS가 약 50% 이하일 때 20% 이상이었다. 약 75% 이상에서는 10% 이하로 줄었다. 이 교차 구간은 이 기계·브라우저·목록 모양에서 관찰한 것이다. 다른 환경에서는 다시 재야 한다.
- **mini-react의 선택:** 기본값을 LIS로 둔다. 판단 근거는 두 가지다.
  - 흔한 "일부 이동" 갱신에서 commit을 크게 줄였다.
  - 불리한 조건에서 잃은 것은 측정 흔들림 안이었다.

## 6. 한계

- **시간 흔들림:** IQR/중앙값이 모든 조건에서 5%를 넘었다(10~87%). 그래서 모든 조건을 63회까지 반복했다. 10% 안팎의 시간 차이는 결론에 쓰지 않았다.
- **환경 하나:** 한 대의 Windows 기계, Claude 데스크톱 앱에 내장된 Chrome 152에서만 쟀다. 다른 브라우저·기기·전원 상태는 재지 않았다.
- **재지 않은 것:**
  - 강제 layout 시간, 힙 사용량, Chrome 성능 trace
  - 페인트까지 포함한 화면 갱신 시간
- **작업 생성기의 범위:**
  - 이동 비율 k는 "무작위 위치로 이동"만 썼다.
  - Block Shift는 시드 하나(덩어리가 뒤로 가는 경우)만 쟀다. 앞으로 가는 덩어리는 B에 더 불리할 것으로 예상하지만 재지 않았다.
- **배치 측정:** N<100의 배치 측정은 단일 측정보다 7~13% 높게 나왔다(N=100·500 비교). 작은 N의 절대값은 이 차이를 감안해야 한다.
- **React 비교:** React는 구현 전체가 다르므로 A·C 차이를 이동 판단 하나로 설명하지 않는다. React의 프로덕션 UMD는 개발용 경고가 없지만, `createRoot`·`flushSync` 경로가 실제 앱의 동시성 렌더링과 같지는 않다.
- **정확성 검사:** "이 생성기와 검사 항목으로는 왜곡을 탐지하지 못했다"는 뜻이다. 모든 입력에서 같다는 증명이 아니다.
