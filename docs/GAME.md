# NEON SURVIVOR — 게임 특화 Mini React

## 실행

```sh
npm ci
npm run dev
# http://127.0.0.1:5173/game.html
# http://127.0.0.1:5173/experiment.html
npm test
PLAYWRIGHT_CHANNEL=chrome npm run test:e2e
npm run build
```

`index.html`은 기존 과제, `game.html`은 게임, `experiment.html`은 Mini React와 실제 React를 비교하는 실험실입니다. Vite 프로덕션 빌드는 세 진입점을 모두 포함합니다. React/React DOM은 비교용 개발 의존성이며 실험실에서 React를 측정할 때 로드합니다.

## 게임

WASD 또는 방향키로 이동합니다. 가장 가까운 적을 향해 자동 발사하고 3분 동안 살아남으면 승리합니다. 몹에 닿으면 체력이 감소하며 피격 직후 650ms 동안 추가 피해를 받지 않습니다. 처치한 적의 경험치는 즉시 획득합니다. 레벨업 때 과충전(공격력 +1), 속사(공격 속도 ×1.2, 최대 4배), 가속(이동 속도 +20, 최대 300) 중 하나를 선택합니다. 버튼 또는 숫자 1/2/3으로 선택할 수 있습니다.

Escape/Space 또는 오른쪽 위 버튼으로 일시정지합니다. 탭 숨김/창 포커스 상실도 일시정지하며 입력과 누적 시간을 초기화합니다. 레벨업과 일시정지 동안 게임 시간은 흐르지 않습니다. 패배/승리 뒤 다시 도전하면 같은 초기 시드로 새 게임을 시작합니다. 첫 버전은 데스크톱 키보드 조작을 대상으로 하며 모바일에는 안내와 반응형 화면만 제공합니다.

기본 게임은 960×540의 고정 논리 좌표, 몹 300개/투사체 128개의 표시 슬롯을 사용합니다. 빈 슬롯이 없으면 생성을 생략합니다. 적은 시간에 따라 생성 빈도·이동 속도·체력이 증가합니다. 게임 상태·입력·난수 시드는 루트 `useState`에 있으며 자식 HUD/Overlay는 stateless입니다. 모델 함수는 DOM이나 브라우저 시계를 읽지 않습니다.

## 엔진 API

```ts
import { useFrame, useScene, useState } from './core/component';
import { h } from './core/element';
import { advanceGame, createGame, sceneSlots } from './game/model';

function App() {
  const [game, setGame] = useState(() => createGame());
  useFrame(({ time, delta }) => {
    // time: rAF timestamp, delta: 직전 활성 프레임과의 차이 (둘 다 ms)
    setGame(previous => advanceGame(previous, delta));
  }, game.phase === 'running');
  const scene = useScene(sceneSlots(game));
  return h('section', null, scene);
}
```

### useFrame(callback, enabled = true)

루트 렌더 중에만 호출합니다. Hook 순서는 매번 같아야 합니다. 루트당 rAF 예약은 하나이며 활성 Frame Hook들을 호출한 뒤 상태 변경을 한 번 렌더링합니다. 같은 슬롯의 함수형 updater는 호출 순서대로 누적됩니다. 일반 이벤트의 setter는 기존처럼 동기 갱신합니다. Effect 안의 상태 갱신도 기존 정책을 유지합니다.

첫 프레임과 재활성화한 첫 프레임의 delta는 0입니다. 마지막으로 commit된 콜백을 사용하며 실패한 렌더의 콜백을 채택하지 않습니다. 비활성화/unmount는 예약을 취소하고 시간을 초기화합니다. 프레임 콜백/렌더 오류가 나면 루프를 중단합니다. 게임은 이 API 위에서 60Hz 고정 시뮬레이션을 최대 5단계 따라잡고 초과 시간을 `droppedMs`에 기록합니다. 프레임을 느리게 처리하면서 단계를 버린 결과를 더 빠른 처리량이라고 주장하지 않습니다.

### useScene(slots)

입력은 읽기 전용 `SpriteSlot[]`입니다. 각 항목은 `entityId`, `kind`(player/enemy/bullet), `x`, `y`, `active`, 선택적인 `hit`를 가집니다. 반환값은 `h()` 자식으로 넣는 불투명한 장면 표현입니다. 장면 자체나 반환 VNode를 수정하지 마세요.

슬롯 순서가 DOM 동일성을 결정합니다. 엔티티가 죽어도 배열에서 삭제하거나 정렬하지 않고 active=false로 유지하며, 새 엔티티가 그 슬롯을 재사용합니다. 이는 일반 keyed reconciliation을 구현한 것이 아닙니다. 배열 길이 변경은 기존 인덱스 Diff로 처리하지만 일반 플레이에서는 용량을 고정합니다.

각 슬롯은 `<i>` 하나, 장면은 `.scene` 요소 하나가 됩니다. 위치는 두 소수점 자리로 표시하고 기존 속성 Patch로 CSS transform을 적용합니다. 이벤트/자식 요소가 없는 평면 스프라이트 전용입니다. 메뉴와 입력은 일반 `h()`로 작성합니다.

표시 데이터가 같은 슬롯은 동결된 VNode를 공유합니다. 모든 슬롯이 같으면 장면 VNode도 공유합니다. Diff는 동일 참조를 만나면 재귀 비교를 생략합니다. 루트 소유 캐시는 입력 표시 데이터를 복사하며 렌더가 성공한 뒤에만 확정됩니다. 따라서 호출자가 다음 프레임의 객체를 수정해도 이전 캐시를 덮어쓰지 않습니다. 모든 몹이 움직이면 여전히 각 몹의 위치를 비교·Patch해야 합니다.

### 선택적 진단

`FunctionComponent` 생성자의 기존 네 번째 RenderObservation 콜백은 그대로 유지합니다. 선택적인 다섯 번째 콜백은 `{renderMs, diffMs, patchMs, operations}`를 받습니다. `renderMs`는 루트/자식 실행과 VDOM 변환을 포함합니다. `operations`는 Patch 작업 개수이며 DOM API 호출 횟수나 React 내부 작업 횟수와 같은 지표가 아닙니다.

일반 실행은 타이밍 호출을 하지 않습니다. 진단 실행과 본 성능 측정은 분리하며, 기존 상세 관찰을 켜면 이전 트리를 복제하는 비용이 추가되므로 성능 측정에 사용하지 않습니다.

## 공정한 비교

네 비교 구현은 동일한 고정 슬롯·DOM 모양·시뮬레이션을 사용합니다. 일반 Mini React도 프레임당 한 번만 상태를 변경합니다. React에는 기본 구현과 스프라이트별 React.memo 구현을 모두 제공하며 flushSync로 동기 실행을 강제하지 않습니다. React Compiler는 이번 비교에서 사용하지 않으므로 결과를 Compiler 적용 React 전체로 일반화할 수 없습니다.

실험실의 이동/생성·사망/정지는 사전 생성된 장면 기록을 재생합니다. 게임 전체는 실제 전투 모델·입력·충돌과 장면 렌더링을 포함하는 자동 진행 부하입니다. 실제 플레이와 달리 처리량 비교를 위해 받아들인 프레임마다 한 시뮬레이션 단계를 진행하고 레벨업을 자동 선택하며 사망하면 재시작합니다. 지정 몹 수는 이 시나리오의 초기 수량이며 처치로 감소할 수 있습니다. UI 메뉴 조작의 응답성은 기능 테스트 대상으로 분리합니다.

프레임 수/단계 수가 다른 두 실행의 최종 체크섬 자체를 직접 비교하지 않습니다. 각 실행이 처리한 정확한 단계 수와 같은 입력으로 종료 후 재시뮬레이션하여 일치 여부를 확인합니다. 최종 DOM도 기대 슬롯 데이터와 대조합니다. 이 작업은 측정 구간에서 제외합니다.

실험실의 기본 조합은 특화 Mini React와 기본 React입니다. 두 렌더러는 같은 시나리오·몹 수·시드로 한 번에 하나씩 실행됩니다. 비교 상대에서 단일 측정을 선택할 수도 있습니다. 3·10·20·60초 중 하나를 고르면 렌더러당 예열 시간과 예상 총 시간이 표시됩니다. 측정 결과와 실행 설정은 JSON 또는 CSV로 내보낼 수 있습니다. 성능을 비교할 때는 `npm run build && npm run preview`를 실행한 뒤 출력된 주소의 `/experiment.html`을 여세요.

끊김을 비교할 때는 프레임 간격 p95와 60Hz 예산 초과율부터 보세요. p95는 측정값의 95%가 그 수치 이내라는 뜻입니다. FPS가 약 60으로 비슷해도 DOM 반영 p95에는 차이가 있을 수 있습니다. DOM 반영 시간은 스케줄러 대기를 포함하며 브라우저의 화면 그리기 시간은 별도로 측정하지 않습니다. 짧은 실험에서 수치 차이가 작다면 같은 조건에서 반복해 확인하세요.

## 검증 범위

단위 테스트는 순차 updater 배칭, 콜백 갱신/정리/루트 격리/실패한 렌더, 장면 DOM 동일성·캐시·슬롯 재사용·잘못된 좌표, 모델 재현성·충돌·성장·승패·포화·지연 제한을 다룹니다. 브라우저 테스트는 키보드 이동, 포커스, blur 이후 입력 해제, 레벨업 정지/선택, 패배와 반복 재시작, 두 Mini 렌더러의 측정 정확성을 확인합니다. 기존 Phase 1·2 및 월드컵 회귀 테스트도 유지합니다.

## 기능별 효과를 구분하는 방법

- 프레임 배칭은 동일한 프레임에서 세 번 상태를 증가시키는 단위 실험으로 확인합니다. 일반 rAF의 동기 setter 세 번과 useFrame의 배칭을 비교하며 최종 상태는 같아야 합니다. 정식 성능 측정에서는 모든 렌더러가 프레임당 한 번만 상태를 전달하므로 이 배칭 차이를 인위적으로 성능 우위로 만들지 않습니다.
- 슬롯 재사용은 인덱스 기반 Diff에서 1,000개 목록의 첫 항목을 삭제·압축하는 경우와 첫 슬롯을 비활성화하는 경우의 Patch 작업 수로 확인합니다. 후자는 비활성 DOM을 유지하는 공간 비용을 지불합니다. 이는 React에 없는 기능이라는 주장이 아니며 네 렌더러 모두 같은 슬롯 정책을 사용합니다.
- 장면 변환/캐시 효과는 같은 입력·슬롯 정책의 mini-baseline과 mini-scene을 비교합니다. 별도 진단에서 이동 장면은 같은 수의 위치 Patch를 실행하는지, 정지 장면은 모두 Patch 0개인지 함께 확인합니다.

useFrame 콜백의 배칭 범위는 동기 실행 부분입니다. await 이후의 상태 변경이나 별도 타이머/이벤트는 해당 프레임 배칭에 포함되지 않습니다.

원자료의 `frames`와 시간 표본은 측정 구간만 포함하고, `simulationSteps`와 최종 체크섬은 준비 구간부터 종료까지의 전체 진행을 포함합니다.
