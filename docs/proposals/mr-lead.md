# 제안서: 총괄(mr-lead) 관점

기준: `dev` 5cbca8b. 근거 자료: `docs/requirements-checklist.md`(요구사항별 상태), 아래 기준선 측정.

## 1. 현재 위치

- 과제의 필수 요구사항(Phase 1·2·연계·테스트)은 모두 충족이다. 남은 것은 "포트폴리오 수준"과 "차별점", 중점 포인트 일부 설명(Document/Window, 변화 감지 API, 컴포넌트 분할, State 위치, React 차이 표).
- 이미 강한 것: 정확성(엣지 케이스·실패 복구·fuzz), 학습용 종합 페이지(렌더 파이프라인·LIS 시각화).
- 약한 것: **숫자가 없다.** "바뀐 부분만 고친다"를 말로는 설명하지만, 얼마나 적게·빠르게 고치는지 재현 가능한 측정이 없다.

## 2. 기준선 측정 (총괄이 먼저 잰 값)

Node 22 + jsdom 26, `render()` 한 번, 행 = `<tr key><td>id</td><td>label</td></tr>`.
MutationObserver 기록 수는 결정적(매번 같음), 시간은 jsdom이라 참고용(브라우저와 다름).

> **정정(mr-perf 지적):** 이 스크립트는 한 jsdom 문서에서 render를 이어 불러 남은 노드 때문에 삽입 시간이 2~3배 부풀었다. 실행마다 새 창으로 잰 값은 빈 tbody 1k 생성 105ms(한 번에 넣어도 106ms)다. 아래 시간 열은 비교에 쓰지 말고, 기록 수만 유효하다. 정식 수치는 `docs/bench/`(mr-perf).
스크립트: 공유 노트 폴더의 `lead-baseline-bench.mjs` (실행: `node lead-baseline-bench.mjs file:///<repo 경로>`) (mr-perf가 정식 `npm run bench`로 옮기길 제안).

| 시나리오 (1k행) | 패치 수 | DOM 변경 기록 | jsdom 시간 |
|---|---:|---:|---:|
| 빈 tbody에 1k 생성 | 1000 | 1000 | 184ms |
| 10행마다 텍스트 갱신 | 100 | 100 | 34ms |
| 두 행 swap(1↔998) | 2 | 4 | 21ms |
| 역순 | 999 | 1998 | 127ms |
| 맨 앞에 1행 삽입 | 1 | 1 | 26ms |
| 한 행 삭제 | 1 | 1 | 22ms |
| 전체 삭제 | 1000 | 1000 | 24ms |
| 빈 tbody에 10k 생성 | 10000 | 10000 | 795ms |

읽은 것:
- 부분 갱신·swap·삽입·삭제는 이미 최소(LIS 덕분에 swap이 MOVE 2번, 역순은 n-1번 = 이론 최소).
- **대량 생성·전체 삭제는 행마다 DOM 연산 한 번씩**이다. 연속 CREATE를 DocumentFragment 하나로 묶거나, 자식을 모두 지울 때 한 번에 비우는 빠른 경로가 있으면 DOM 변경 기록(=브라우저가 처리할 삽입 횟수)이 1000 → 1로 줄어든다. 단 실제 브라우저 시간 이득은 측정해서 확인해야 한다.
- diff 자체 비용(`collectNodes`가 매 diff마다 이전 트리 전체를 Set에 담음 등)은 아직 따로 재지 않았다.

## 3. 특화 분야 후보

| 후보 | 내용 | 장점 | 위험 |
|---|---|---|---|
| **A. "최소 DOM 변경을 증명하는 엔진" (추천)** | 표준 벤치마크 시나리오(js-framework-benchmark와 같은 생성·갱신·swap·삭제·clear)에서 DOM 변경 수가 이론 최소임을 테스트로 고정하고, 대량 생성·삭제 빠른 경로로 수치를 낮춘다. 실제 React 방식(lastPlacedIndex)·key 없는 비교·innerHTML 전체 교체와 같은 시나리오로 비교표를 만든다 | 숫자로 말할 수 있다. 정확성(dx)과 성능(perf)이 같은 지표(DOM 변경 수)로 만난다. 지표가 결정적이라 CI 성능 예산으로 쓸 수 있다 | jsdom 시간은 브라우저와 다르다 → 시간은 브라우저 벤치 페이지에서 따로 잰다 |
| B. 학습·디버깅 도구 | 렌더 타임라인, 훅 상태 검사기, 패치 재생 | 이미 강점. 면접 시연에 좋음 | 남들도 하기 쉬움. 수치 없음 |
| C. 정확성 보증 | 속성 기반 fuzz(차등 오라클: 새로 그린 DOM과 비교), 훅 규칙 정적 검사 | 신뢰도 | 겉으로 덜 보임 |

**제안: A를 간판으로, C를 A의 근거로, B는 A의 결과를 보여 주는 화면으로.**
즉 "DOM을 적게 바꾸는 미니 React — 그리고 그것을 측정·증명하는 도구"를 한 문장 이야기로 만든다.

## 5. 성능 예산 초안 (3단계 ADR에서 확정)

- **강한 예산(CI, 실패하면 병합 안 함)**: 시나리오별 DOM 변경 기록 수 상한. 예: 1k 중 10행마다 갱신 ≤ 100, swap ≤ 4, 맨 앞 삽입 ≤ 1, 한 행 삭제 ≤ 1, 역순 ≤ 2(n-1). 빠른 경로가 들어가면 생성·clear 상한을 낮춘다.
- **약한 예산(기록만)**: jsdom·브라우저 시간 중앙값. 기준 대비 20% 넘게 느려지면 PR 본문 "남은 경고"에 적고 이유를 설명한다. 시간은 환경 잡음이 커서 CI 실패 조건으로 쓰지 않는다.

## 6. 위험과 대응

| 위험 | 대응 |
|---|---|
| 최적화가 코드를 설명하기 어렵게 만든다 (과제 원칙: 핵심 로직을 설명할 수 있어야 함) | 빠른 경로마다 주석과 테스트 이름으로 "왜·언제" 설명. 설명 못 하는 최적화는 채택하지 않는다 |
| 두 세션이 같은 파일(`src/diff/*`)을 동시에 고친다 | 파일 소유: perf = `src/diff/`, `bench/`·`demo/bench/`; dx = `demo/`(bench 제외), `docs/`, fuzz·데모 테스트. 남의 영역 변경은 상대에게 먼저 알리고 브랜치를 작게 |
| jsdom 시간을 브라우저 성능처럼 말한다 | 문서에 환경을 항상 적고, 결정적 지표(변경 수)와 시간 지표를 분리 |
| 범위가 커져 마무리를 못 한다 | P1을 먼저 dev에 넣는다. P3는 시간이 남을 때만 |
| 패치 순서·폼 상태 같은 기존 엣지 케이스 회귀 | 237개 테스트 + fuzz가 병합 게이트. 빠른 경로는 fuzz 시나리오에 반드시 포함 |

## 7. 다른 두 세션에게 묻고 싶은 것

- perf: 연속 CREATE 묶기·clear 빠른 경로가 실제 브라우저 시간도 줄이는지(측정 계획), diff 쪽 비용(collectNodes, own/clone)은 얼마인지.
- dx: 빠른 경로가 깨뜨릴 수 있는 엣지 케이스 목록(select value 순서, 폼 상태, 같은 vnode 재사용, patch 실패 복구)과 그것을 잡을 fuzz 설계.
- 둘 다: 특화 분야 A에 동의하는지, 아니면 데이터로 다른 안을 제시할지.
