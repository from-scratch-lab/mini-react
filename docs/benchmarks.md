# 벤치마크

대량 목록(js-framework-benchmark와 같은 1,000행 표)을 조작할 때 mini-react가 하는 일을 숫자로 남긴다.

- 실행: `npm run bench` (1k, 11회 중앙값) · `npm run bench -- --rows 10000 --runs 1 --warmup 0` (10k)
  · `npm run bench -- --only swap` (시나리오 하나) · `--json docs/bench/<이름>.json` (원자료 저장)
- 성능 예산(CI): `tests/bench/budget.test.js`가 아래 결정적 지표 넷의 시나리오별 상한을 검사한다.
- 코드: `scripts/bench/scenarios.js`(시나리오·지표), `scripts/bench/run.js`(시간), `scripts/bench/react-moves.js`(이동 수 비교)

## 지표

| 지표 | 뜻 | 결정적? |
|---|---|---|
| 패치 | diff가 만든 패치 수 | 예 |
| 기록 | MutationObserver 기록 수 (DOM이 바뀐 횟수) | 예 |
| 붙임+뗌 | 기록 안 addedNodes + removedNodes 합 = 붙이거나 뗀 하위 트리 뿌리 수. 하위 트리를 통째로 붙이면 1, 옮기기 1번은 2 | 예 |
| 새 노드 | patch 뒤 컨테이너 안에 새로 생긴 노드 수 (만드는 API와 상관없이) | 예 |
| 이동 | 엔진의 MOVE 수 / LIS 이론 최소 / 같은 key 순서를 React식(`lastPlacedIndex`)으로 처리할 때 | 예 |
| diff ms, patch ms | 중앙값. **jsdom 기준 참고값**, 실행마다 ±30% | 아니오 |

측정 방식 주의: 실행마다 새 jsdom 창, 시나리오마다 새 Node 프로세스. 한 문서에서 계속 재면 남은 노드 때문에 삽입 시간이 2~3배 부풀고, 닫은 창도 메모리가 다 풀리지 않는다.
행의 핸들러는 실제 앱처럼 렌더마다 새 화살표 함수다.

## 기준선에서 읽은 것

1. **이동은 이미 최소다.** 엔진의 MOVE 수가 LIS 이론 최소와 같다. 같은 key 순서를 React식으로 처리하면 swap은 997번(10k는 9,997번), 맨 뒤 → 맨 앞은 999번 옮긴다. React는 "지금까지 제자리에 둔 노드 중 가장 뒤의 이전 위치"보다 앞에 있던 노드를 모두 옮기기 때문이다. 우리와 Vue 3는 LIS로 그대로 둘 노드를 고른다.
2. **핸들러 때문에 렌더마다 PROPS가 행마다 2개 생긴다.** 같은 데이터로 다시 그려도 패치 2000개, DOM 변경 0. 갱신 시나리오의 diff 시간(13~15ms) 대부분은 DOM을 바꾸지 않는 비교 작업이다.
3. **빈 tbody 생성·덧붙이기·지우기는 행마다 DOM 연산 1번**(기록 1000). jsdom에서는 자식이 많은 부모에 하나씩 넣고 빼는 비용이 행 수보다 빠르게 커진다(10k 덧붙이기 10초, attach 지우기 43초). 브라우저에서도 그런지는 브라우저 벤치 페이지에서 따로 잰다.

개선 계획과 순서는 `docs/decisions/0001-plan.md`(ADR 0001)를 따른다. 최적화 브랜치는 이 표에 "변경 전 → 후"를 더하고 예산 상한을 낮춘다.

## 개선 기록

### 1. 핸들러 교체를 패치에서 빼기 (`feat/perf-handler-box`, 설명: `docs/perf/handler-box.md`)

결정적 지표 (1k, 기록·붙임+뗌·새 노드 수는 모든 시나리오에서 변화 없음):

| 시나리오 | 패치 전 → 후 |
|---|---|
| 같은 데이터 다시 렌더 | 2000 → **0** |
| 10행마다 갱신 | 2100 → **100** |
| 한 행 선택 | 2001 → **1** |
| 두 행 swap | 2002 → **2** |
| 맨 뒤 → 맨 앞 | 2001 → **1** |
| 뒤집기 | 2999 → **999** |
| 한 행 삭제 | 1999 → **1** |
| 1k 뒤에 1k 추가 | 3000 → **1000** |
| 생성·교체·지우기·attach 시나리오 | 그대로 (이전 핸들러가 없거나 문자열 → 함수라 원래 PROPS) |

이제 갱신 시나리오에서 **패치 수 = 실제로 DOM을 바꾸는 일의 수**다(MOVE는 기록 2개라 기록 수와 같지는 않다).

시간 (jsdom, 이전·이후 코드를 번갈아 15회 × 3라운드, 라운드별 중앙값의 중앙값):

| 시나리오 | diff ms 전 → 후 | patch ms 전 → 후 |
|---|---|---|
| 같은 데이터 다시 렌더 | 13.8 → 13.2 | 1.26 → 0.81 |
| 10행마다 갱신 | 15.8 → 13.2 | 1.92 → 1.41 |
| 한 행 선택 | 16.0 → 13.0 | 1.35 → 0.88 |

diff는 5~18%, patch는 30~40% 줄었지만 라운드 사이 흔들림(최대 2배)이 그보다 커서 **시간 이득은 주장하지 않는다.**
diff 시간의 대부분은 핸들러가 아니라 노드 순회·할당 비용이다(다음 개선 대상: `diffChildren` 빠른 경로, VNode 생성 비용).

### 2. 연속 삽입 묶기 · 전체 지우기 한 번에 (`feat/perf-batch-insert`, 설명: `docs/perf/batch-insert.md`)

결정적 지표 (1k, 패치 수·붙임+뗌·새 노드 수는 그대로 — 패치 목록은 diff가 만든 그대로이고 DOM에 알리는 횟수만 줄었다):

| 시나리오 | DOM 변경 기록 전 → 후 |
|---|---|
| 생성 (빈 tbody) | 1000 → **1** |
| 1k 뒤에 1k 추가 | 1000 → **1** |
| 전체 지우기 | 1000 → **1** |
| 전체 교체 | 2000 → **2** |
| attach: 전체 지우기 | 1000 → 1000 (가상 트리에 없는 공백 텍스트가 있어 빠른 경로를 쓰지 않음) |

시간 — **브라우저**(Chrome 152, 1,000행, 레이아웃 강제 포함, 두 방식을 번갈아 30회 중앙값):

| 연산 | 하나씩 | 한 번에 |
|---|---:|---:|
| 빈 tbody에 1,000행 넣기 | 36.5ms | 36.2ms |
| 1,000행 뒤에 1,000행 덧붙이기 | 117ms | 113ms |
| 1,000행 지우기 | 7.8ms | 6.7ms |

시간 — jsdom(이전·이후 코드를 번갈아): 덧붙이기 167~195 → 107~116ms로 빨라졌지만, 지우기는 16 → 43~50ms로 **느려졌다**
(jsdom의 `textContent` 구현이 이 행 구조에서 느림. 같은 jsdom에서 단순 목록은 `textContent`가 8배 빠르다).

결론: **브라우저 시간 이득은 거의 없다**(지우기 약 14%, 넣기는 차이 없음). Chrome은 레이아웃을 읽을 때까지 미뤄 두므로
하나씩 넣어도 레이아웃을 1,000번 계산하지 않는다. 이 개선의 가치는 ① DOM 변경 알림 1000 → 1(MutationObserver를 쓰는 코드·확장 프로그램의 비용),
② 빈 `<select>`에 option을 넣을 때 마지막 option이 선택되던 버그(B6)를 함께 고친 것이다.

### 3. 자식 비교 빠른 경로 (`feat/children-fastpath`)

`diffChildren`이 목록 앞뒤의 같은 key 구간은 이름표·Map·LIS 없이 바로 짝지어 비교하고, 가운데 구간만 일반 알고리즘(key 짝 찾기 → LIS)을 쓴다.
가운데가 모두 짝이 있고 순서도 같으면 LIS를 건너뛴다.

- **패치 목록은 그대로**: 이전 코드 사본과 무작위 트리 20,000쌍 + "조금 고친 목록" 20,000쌍을 비교해 내용·순서가 모두 같았다(불일치 0). 결정적 지표(패치·기록·붙임+뗌·새 노드)는 모든 시나리오에서 그대로다.
- 시간 (jsdom, 1k, 11회 중앙값, 같은 기계에서 바로 앞 dev와 비교):

| 시나리오 | diff ms 전 → 후 |
|---|---|
| 같은 데이터 다시 렌더 | 11.3 → 8.4 |
| 10행마다 갱신 | 11.1 → 7.9 |
| 한 행 선택 | 12.5 → 8.4 |
| 두 행 swap | 10.6 → 8.9 |
| 뒤집기 | 15.4 → 8.3 |

ADR 0001의 목표(같은 데이터 diff ≤ 10ms)를 맞췄다. jsdom 시간이라 ±30% 흔들리므로 방향만 본다.
